# FORTE mutation results

Generated by `python3 scripts/fbt_mutation_campaign.py`. Do not edit by hand, except through
`corpus/fbt_mutation_survivor_notes.json`.

Each mutant is one edit to the ST algorithm text of the deterministic translator's .fbt. It runs through
the exporter, g++ and **real FORTE**, and its trace is compared with **unmutated matiec**. This is a
different experiment from `docs/MUTATION_RESULTS.md`, which compares matiec with mutated matiec and does
not involve FORTE.

Run with `--count 5 --seed 61499`, in 509 s.

**Detected: 98 of 105 counted mutants (93.3%)**: 98 different, 0 crashed, 0 timed out. 7 survived. 0 failed to compile and are not counted.

How to read this:

- 21 programs at 5 mutants each is a small sample, far smaller than the exhaustive matiec
  campaign. A confidence interval on a rate from this few mutants would be wide.
- `select_mutants` takes kinds in sorted order, so at 5 per program it takes boundary, constant, negate,
  operator and remove in turn. Branch swaps are not sampled at this count unless a program lacks one of
  those kinds. The kind table below shows what was actually run.
- The .fbt text includes the lowered standard FBs, so some mutants hit the timer and counter logic that the
  translator inlined. The ST-level campaign cannot reach those lines.
- The corpus is self-authored. See `docs/CORPUS.md`.
- The ECC is not mutated. The translator's only guards are `REQ` and `1`, so there is nothing to mutate in
  it that is more interesting than a missing CNF, which `tests/test_forward_e2e.py` already covers.

## Earlier survivors, from before this campaign

### 13_case_sequencer `mutant_010`: removed `STEP_TIMER_STATE := 2;`

Sampled before this campaign, with `mutate fbt --count 12`, in `build/val_forward/13_case_sequencer/mutants/`. Run again for this report: it is equal to matiec on the tuning stimulus (1134 scans, 3 changes of STEP_TIME) and on the held-out stimulus (1469 scans, 11 changes of STEP_TIME).

Analysed: equivalent **for this program**, reasoned and not proved. It is not an equivalent mutation of TON in general.

With the statement gone, STATE stays 1 after expiry instead of moving to 2. Going through the lowered TON:

- The start branch needs STATE = 0, and neither 1 nor 2 is 0, so it does not change.
- The `NOT IN` branch does not look at STATE, so it resets the timer exactly as before.
- That leaves IN still true with STATE 1, which reruns the expiry test on every call. If it holds it writes Q := TRUE and ET := PT, which they already are. If it fails, because PT rose after expiry, it writes only ET := NOW - START. So Q does not change.
- This program reads only `STEP_TIMER.Q`. ET is not read by any statement, and no output shows it.

So Q is the same on every scan for every input sequence, and that holds even though STEP_TIME is an input that changes. The difference is real but lies entirely in ET: the same removal in a program that outputs ET and raises PT after expiry while IN holds is visible, and Findings below shows exactly that on real FORTE.


## Findings

**No pipeline bug was found.** All 21 controls are equal, and every detected mutant was detected by a trace difference, with no crash, timeout or compile failure.

**A real gap in a tuning stimulus, found by following up `mutant_010`.** Its argument depends on ET being unread, and `10_valve_feedback` does output a timer's ET as `TRAVEL_TIME`, so the same mutation should be visible there. An exhaustive run over that one program gave 111 mutants, 99 different and 12 survivors. To reproduce: `python3 scripts/fbt_mutation_campaign.py --only 10_valve_feedback --count 1000 --save-json build/fbt_valve_all.json`, 463 s here.

- `OPENING_TIMER_STATE := 2` and `CLOSING_TIMER_STATE := 2`, each removed or changed to `:= 1`, are 4 of those 12. All 4 survive `stimulus.json`, and are **not equivalent**. A hand-written stimulus (open command held, limit switch never made, TRAVEL_LIMIT 30 ms for 6 scans and then 500 ms) gave matiec `TRAVEL_TIME` holding at 30 where the mutants of the opening timer went to 60 on scan 6, on real FORTE. The unmutated translation matched matiec on the same stimulus.
- No tuning stimulus raises a timer's PT after it has expired while IN holds, so a translator bug in this corner would pass the tuning stimulus of this program.
- `corpus/generate_heldout.py` gained a retune phase because of this, and all 4 now fail on `heldout_stimulus.json`. `tests/test_llm_e2e.py` uses one of them as the real example of a candidate that passes tuning and fails held-out.
- The tuning stimulus was deliberately left unchanged, because the task says that existing stimulus files must not change. Whether to add this corner to `stimulus.json` is a decision for the project owner.
- The other 8 of the 12 are not separately analysed here. They are the same kinds of change as the survivors above (the start condition's `AND` to `OR`, `2` to `3`, removing `Q := FALSE` or `PREV_IN := IN`) on either timer, and they survive both stimuli.

**The exporter accepts what matiec rejects.** Removing the only statement of a branch compiles on this path, whereas matiec rejects an empty branch (`docs/CORPUS.md`). This is why this campaign has no compile failures, while the matiec one has many. It is not a behaviour bug, since an empty ST branch does nothing either way.

**Line numbers in mutant descriptions run one ahead of the algorithm text**, because the CDATA section starts with a newline. They are correct for the text inside the CDATA, and `line 45` is line 44 of the `Algorithm.st` string.
